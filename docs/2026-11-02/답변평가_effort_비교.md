# 답변 평가 도구와 effort 비교 (2026-11-02)

## 1. 왜 하는가

채팅 화면에서 시간을 재 보니 답변 LLM(Sonnet)의 첫 글자가 늦었다. 토큰을 재 보니 답변 출력 1,246개 중 **생각(thinking) 토큰이 740개(59%)** 였다. 생각 양은 effort로 직접 줄일 수 있지만, 지금까지는 검색 지표만 재서 답변이 나빠져도 알 수 없었다. 그래서 답변 품질을 재는 도구를 먼저 만들고, 그 도구로 effort를 비교한다.

예제 노트북 006(생성·평가)의 방식(임베딩·크로스 인코더 유사도, LLM 채점)을 참고했다.

## 2. 평가 도구 (`scripts/eval_answers.py`)

평가셋 질문마다 챗봇과 같은 과정(M4b 검색 + 리랭크 + 답변 LLM)으로 답변을 만들고 기대 답과 비교한다.

| 층 | 지표 | 어디서 | 내용 |
|---|---|---|---|
| 규칙 | 숫자 포함 | 로컬 | 기대 답의 수(금액·일수 등, 만·억 단위 환산) 중 답변 본문에 있는 비율 |
| 규칙 | 정답 인용 | 로컬 | 근거 줄의 `[번호]`가 가리키는 발췌 중 정답 조문이 있는가 |
| 규칙 | 근거 줄 | 로컬 | 근거 줄이 있는가 |
| 규칙 | 거절 판단 | 로컬 | 규정에 없는 질문은 "찾을 수 없습니다", 정답 있는 질문은 거절하지 않았는가 |
| 유사도 | 크로스 인코더 | 로컬 | 기대 답 ↔ 답변 본문 (리랭커 모델 재사용). 참고 지표 |
| LLM 판정 | 맞음 1 / 부분 0.5 / 틀림 0 | 외부 API | 기대 답을 정답으로 보고 판정. 표현 차이와 어긋나지 않는 추가 설명은 감점하지 않는다 |

- 시간·토큰: 답변 LLM 호출만 잰다 (첫 본문 글자, 답변 완료, 입력·생각·본문 토큰).
- 여러 effort를 비교할 때는 같은 질문·같은 발췌로 질문마다 설정을 번갈아 실행한다.
- 화면에는 점수·시간·토큰·질문 id만 나온다. 질문별 답변과 판정 이유는 `data/eval/results/answers-*.csv` (공유 금지).

### 외부 전송 (사용자 결정, 11-02)

| 단계 | 보내는 것 | 받는 곳 |
|---|---|---|
| 답변 생성 | 질문 + 상위 4개 발췌 (채팅과 같은 범위를 50문항 × 설정 수만큼) | 답변 LLM (Sonnet) |
| LLM 판정 | 질문 + 기대 답 + 답변 본문. **발췌는 보내지 않는다** | 판정 LLM (Sonnet, effort low) |
| 다듬기 | 없음 (`--rewrite-from`으로 10-30 저장 검색어 재사용) | – |

## 3. 미리 정한 비교 규칙 (결과를 보기 전에 적음)

| 항목 | 값 |
|---|---|
| 조건 | M4b + 리랭크 후보 5개(입력: 원래 질문), 발췌 4개, 1회 검색어 세트. effort = 기본값(high와 같음) · medium · low |
| 주 지표 | LLM 판정 점수 (정답 있는 45문항) |
| 지킴선 | 거절 판단과 정답 인용이 기본값보다 0.05 넘게 떨어지면 탈락 |
| 선택 | 지킴선을 통과한 설정 중 LLM 판정이 최고 점수와 0.05 이내면 **첫 글자 평균이 가장 빠른 설정** |
| 한계 | LLM 판정은 판정 모델의 기준에 따른다. 판정 이유는 CSV에서 사람이 일부 확인한다 |

"일부 못 찾음"은 따로 센다: 기본값 4개, medium 6개, low 5개 (Q32·Q33·Q37·Q38 공통).

### 5.3 판단

- 지킴선: 정답 인용·거절 판단 모두 1.00으로 세 설정 통과.
- LLM 판정은 0.84~0.87로 모두 최고점과 0.05 이내. 차이(0.01~0.03)는 1문항 안팎이라 품질 차이로 보지 않는다.
- 규칙대로 첫 글자가 가장 빠른 **low 채택**. 첫 글자 3.6초 → 1.1초, 답변 완료 5.4초 → 3.2초 (느린 10%: 9.4초 → 4.7초).
- 사용자가 low의 품질을 걱정했으나(조건·여러 조항 판단 약화 우려), 이 평가셋에서는 조건 판단 1.00, 여러 조항 0.56으로 기본값과 같았다.

### 5.4 남은 약점: 여러 조항

여러 조항 질문은 effort와 상관없이 0.50~0.56이다. 공통 문항(Q32·Q33·Q37·Q38)에서 답변이 "일부를 찾을 수 없다"고 밝힌다. 검색 평가의 여러 조항 Recall@4가 0.69였으므로, 필요한 조문 일부가 LLM에 전달되지 않는 **검색 쪽 문제**로 본다. 생각을 늘려도 해결되지 않는다.

### 5.5 한계

- 평가셋 50문항, 검색어 1세트, 1회 실행. 판정 모델은 Sonnet(effort low) 하나다.
- 보류셋은 기대 답이 비어 있어 검증하지 못했다.

## 7. 발췌 차이 규칙 비교 (current vs narrow)

### 7.1 왜

채팅 테스트에서 답변이 지급 주체가 다른 별개 제도의 금액을 "규정 간 차이"로 짚었다. 충돌이 아닌데 차이로 안내해 사용자를 헷갈리게 하고 답을 길게 만든다. 사용자와 논의해 규칙 자체(같은 규정이 두 곳에 있거나 본문·별표가 어긋날 때 경고)는 필요하다고 보고, 범위만 좁히기로 했다.

| 변형 | 규칙 |
|---|---|
| current (지금) | 발췌끼리 내용이 다르면 어느 발췌가 어떻게 다른지 함께 알립니다. |
| narrow | 서로 다른 규정·제도의 내용은 각각 나누어 안내하고 서로 비교하지 않습니다. 같은 규정의 같은 항목인데 발췌끼리 값이 다를 때만 어느 발췌가 어떻게 다른지 함께 알립니다. |

나머지 프롬프트는 같다. `rag.py`의 `DIFF_RULES`, 평가는 `eval_answers.py --prompts current narrow`.

### 7.2 미리 정한 채택 규칙 (결과를 보기 전에 적음)

| 항목 | 값 |
|---|---|
| 조건 | effort low(.env), 리랭크 5개, 발췌 4개, 1회 검색어 세트, 50문항 |
| 품질 | narrow의 LLM 판정이 current보다 0.05 넘게 낮지 않을 것 |
| 지킴선 | 정답 인용·거절 판단이 0.05 넘게 떨어지지 않을 것 |
| 이득 | 본문 토큰 평균이 줄 것. effort low에서는 생각 토큰이 이미 0에 가까워 시간 이득은 본문 길이에서만 나온다 |
| 보조 | 답변 중 "다르/차이" 표현이 들어간 문항 수 (차이 안내가 줄었는지, 집계만) |
| 판단 | 품질·지킴선을 통과하고 본문이 줄면 narrow 채택. 본문이 줄지 않으면 보조 지표와 함께 다시 판단 |

시험 실행(2문항): 생각 토큰은 둘 다 0, 본문은 current 268 / narrow 360. 2문항이라 판단에 쓰지 않는다.

### 7.3 결과 (50문항, 616초)

상세: `data/eval/results/answers-eval_set-low-current-narrow-rerank5-20261102-170801.csv` (공유 금지).

| 설정 | LLM 판정 | 맞음/부분/틀림 | 숫자 포함 | 정답 인용 | 거절 판단 | 첫 글자 | 답변 완료 | 본문 토큰 | 차이 안내 문항 | 본문 평균 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| current | 0.82 | 30/14/1 | 0.92 | 1.00 | 1.00 | 1.1초 | 3.2초 | 342 | 12/50 | 302자 |
| narrow | 0.84 | 32/12/1 | 0.89 | 0.98 | 1.00 | 1.0초 | 3.0초 | 338 | **6/50** | 300자 |

| 유형 (문항) | current | narrow |
|---|---:|---:|
| 구어체 (7) | 0.86 | 0.93 |
| 단순 사실 (20) | 0.88 | 0.88 |
| 여러 조항 (8) | 0.56 | 0.56 |
| 조건 판단 (10) | 0.90 | 0.95 |

- "차이 안내 문항"은 답변 본문에 `다르·다릅·차이·상이·불일치`가 들어간 문항 수다. "직급에 따라 다릅니다" 같은 일반 표현도 걸리는 거친 지표다.
- **실행 간 흔들림:** 같은 설정(effort low + current)이 5절 실행에서는 0.87, 이번에는 0.82였다. 답변과 판정 모두 LLM이라 실행마다 0.05 안팎 달라진다. 0.05 미만 차이는 품질 차이로 보지 않는다.

### 7.4 판단

- 품질(+0.02)·지킴선(정답 인용 −0.02, 거절 판단 같음) 통과.
- 이득 지표인 본문 토큰은 거의 같다(342 → 338). 규칙대로 보조 지표를 함께 봤다: 차이 안내가 12 → 6문항으로 절반이 됐고 본문 길이는 같다. 별개 제도 비교를 줄인 만큼 제도별로 나눠 안내하는 내용이 채운 것으로 본다.
- **narrow 채택** (`rag.py`의 `DEFAULT_PROMPT_VARIANT`). 이득은 속도가 아니라 **답변의 명확성**(충돌이 아닌 것을 차이로 안내하지 않음)이다.

## 8. OpenAI 전환과 재평가

11-02 저녁 Claude API 크레딧이 소진되어 답변·다듬기 LLM을 OpenAI(`gpt-5.4-mini-2026-03-17`)로 바꿨다 (`.env`의 `LLM_PROVIDER=openai`, `REWRITE_MODEL` 비움).

- `get_llm()`이 OpenAI에도 effort를 `reasoning_effort`로 넘긴다 (minimal·low·medium·high만 받으므로 xhigh·max는 high). 스트리밍 중 토큰 사용량을 받도록 `stream_usage=True`.
- 가상 발췌·가상 질문으로 확인: 첫 글자 0.8초, 답변 완료 1.1초, 근거 줄 형식 정상.
- **5·7절의 결정(effort low, narrow)은 Claude Sonnet 기준이다.** 판정 모델도 OpenAI로 바뀌어 점수를 Claude 결과와 직접 비교할 수 없다. OpenAI 기준선을 새로 잡는다.
- 외부 전송처가 Anthropic에서 OpenAI로 바뀐다 (보내는 범위는 같다).

### 8.1 미리 정한 규칙 (결과를 보기 전에 적음)

3절과 같다. 조건: OpenAI, 프롬프트 narrow, 리랭크 5개, effort 기본값·medium·low. 지킴선(정답 인용·거절 판단 −0.05 이내)을 통과한 설정 중 LLM 판정이 최고점과 0.05 이내면 첫 글자가 가장 빠른 설정을 고른다. 리랭커 본 실험이 끝난 뒤 실행해 CPU를 나눠 쓰지 않게 한다.
