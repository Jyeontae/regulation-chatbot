# 리랭커 M1 실험 기록 (2026-11-02)

## 1. 왜 하는가

10-30에 M4b(검색어 다듬기 + 원래 질문 합치기)를 채택한 뒤 남은 가장 큰 약점은 **정답이 1위로 나오는 비율(Hit@1 0.73~0.76)** 이다. 정답은 상위 4개 안에 거의 다 들어오지만(Hit@4 0.98~1.00) 1등으로 올라오지 못하는 경우가 많다.

리랭커는 "2차 심사위원"이다. 벡터 검색은 질문과 청크를 각각 따로 숫자(벡터)로 바꿔 비교하므로 빠르지만 거칠다. 리랭커(크로스 인코더)는 질문과 청크를 **한 쌍씩 함께** 읽고 관련도를 매기므로 더 정확하지만, 후보 하나마다 모델을 한 번씩 돌려야 해서 느리다. 그래서 벡터 검색으로 후보를 몇 개만 추린 뒤 그 후보만 다시 매긴다.

## 2. 파이프라인

```
질문 → 다듬기 LLM → [원래 질문, 다듬은 검색어]로 각각 벡터 검색 → 높은 유사도로 합침 (여기까지 M4b)
     → 합친 목록의 상위 N개 후보 → 로컬 리랭커(bge-reranker-v2-m3)로 다시 채점·정렬 → 상위 4개 → 답변 LLM
```

- 리랭커는 이 PC에서 돈다. 외부 전송 범위는 M4b와 같다 (다듬기: 질문만, 답변: 질문 + 상위 4개 조문).
- N위 밖 후보는 원래 순서대로 리랭크 결과 뒤에 붙인다 (Hit@10 같은 지표를 계속 잴 수 있게).
- 리랭커 입력 길이는 512토큰(질문 + 청크)으로 자른다. 모델 카드 예시 값이다.

## 3. 바꾼 코드

| 파일 | 내용 |
|---|---|
| `src/regbot/config.py` | `RERANKER_MODEL`(기본 `BAAI/bge-reranker-v2-m3`), `RERANK_CANDIDATES`(기본 0 = 끔) |
| `src/regbot/models.py` | `get_reranker()` — CrossEncoder, 장치는 `EMBEDDING_DEVICE`, `RERANK_MAX_LENGTH = 512` |
| `src/regbot/retriever.py` | `rerank(query, hits, n)` — 상위 n개를 리랭커 점수로 다시 정렬 |
| `scripts/eval_retrieval.py` | `--rerank-candidates N`, `--rerank-query original\|rewrite`, 질문당 리랭크 시간(평균·상위 10% 경계·최소·최대) 출력 |
| `.env.example` | 리랭커 설정 두 줄 |

## 4. 미리 정한 실험 규칙 (결과를 보기 전에 적음)

| 항목 | 값 |
|---|---|
| 비교 조건 | 후보 N = 5 · 10 · 20 × 리랭커 입력 = 원래 질문 · 다듬은 검색어 (6가지) |
| 검색어 | 10-30 M4 두 실행에서 저장한 검색어를 그대로 재사용 (`--rewrite-from`, API 호출 없음). 1회·2회 검색어 세트 모두 잰다 |
| 기준선 | M4b (같은 검색어, 리랭크 없음) |
| 시간 예산 | **리랭크로 늘어나는 시간이 질문당 5초 이내** (사용자 결정, 11-02). 평균과 상위 10% 경계(90번째 백분위수)를 함께 보고, **상위 10% 경계가 5초 이내**여야 예산 안으로 본다 |
| 점수 | MRR@10 (Hit@1 개선이 목표라 1위 여부와 순위를 함께 반영하는 지표). Hit@1은 함께 기록한다 |
| 지킴선 | Hit@4가 기준선보다 낮아지면 탈락 (LLM에 가는 4개에서 정답이 빠지면 안 된다) |
| 선택 | 예산 안의 설정 중 최고 MRR과 0.05 이내면 가장 빠른 설정 |
| 시간 재는 법 | 모델 로딩과 첫 실행 준비는 서버를 띄울 때 한 번만 드는 비용이라 뺀다. 리랭크 호출 자체만 잰다 |
| 추가 관찰 (11-02 오후) | 답변 평가에서 여러 조항 질문이 가장 약했다(LLM 판정 0.50~0.56, 검색 Recall@4 0.69). 후보를 늘리면 빠진 조문이 상위 4개로 들어오는지 여러 조항 Recall@4를 함께 본다. 선택 규칙은 바꾸지 않는다 |

## 5. 중간 결과

### 5.1 기준선 재현과 첫 시험 (1회 검색어 세트)

| | M4b (재현) | + 리랭크 후보 5개 (입력: 원래 질문) |
|---|---:|---:|
| Hit@1 | 0.76 | **0.80** |
| Hit@4 | 1.00 | 1.00 |
| MRR@10 | 0.86 | **0.90** |

M4b 재현 값은 10-30 기록과 같다. 본 실험(후보 5·10·20 × 입력 2가지 × 검색어 2세트)은 아직 돌리지 않았다.

### 5.2 리랭크 시간이 흔들린 원인

첫 시험의 리랭크 시간이 실행마다 평균 3.4초 ~ 6.7초로 크게 흔들렸다. 입력 길이(질문 + 청크)는 16/50 질문에서 512토큰을 넘어 잘린다.

스레드 수와 실행 방식을 한 프로세스에서 번갈아 2회씩 쟀다 (후보 5개, 50문항, i7-14700HX):

| 스레드 | 실행 방식 | 평균 | 상위 10% 경계 |
|---:|---|---:|---:|
| 20 (기본값) | 5쌍을 한꺼번에 | 2.60초 | 3.63~3.68초 |
| 14 | 한꺼번에 | 3.07~3.30초 | 4.13~4.49초 |
| 8 | 한꺼번에 | 4.09~4.49초 | 5.62~6.11초 |
| 14 | **한 쌍씩** | **2.24~2.29초** | **2.96~3.12초** |
| 8 | 한 쌍씩 | 2.73~2.86초 | 3.88~4.03초 |

- 한꺼번에 돌리면 짧은 쌍도 가장 긴 쌍 길이로 채워(패딩) 계산하므로 한 쌍씩이 더 빠르다. → `rerank()`를 한 쌍씩으로 바꿨다.
- 3회차는 다른 작업과 CPU를 나눠 쓰며 느려져(20스레드 3.06초) 중단했다. 처음의 6.7초도 같은 원인으로 본다. 다른 프로그램이 CPU를 쓰면 시간이 크게 늘어난다는 점은 실사용에서도 고려해야 한다.
- 20스레드 + 한 쌍씩은 아직 재지 않았다. 코드는 스레드 수를 바꾸지 않는다 (기본값).

### 5.3 채팅 화면 연결 (사용자 직접 테스트용)

`chat.py --rerank-candidates N`을 추가했다. 리랭커 입력은 원래 질문이다. 답변 위에 단계별 시간(다듬기·검색·리랭크), 아래에 첫 글자·답변 완료까지의 시간을 보여 준다. 질문부터 답변 완료까지의 전체 시간은 이전에 잰 적이 없다.
