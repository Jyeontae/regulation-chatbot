# 기술 의사결정: 왜 Python 단독으로 구현했는가

| 항목 | 내용 |
|---|---|
| 프로젝트 | 사내 규정 RAG 챗봇 (가상 규정 문서 기반) |
| 결정일 | 2026-10-27 |
| 결정 | 브리프의 "Python(LangChain) + Spring AI 이중 구현"을 버리고, **Python 단독**(FastAPI + LangChain 1.x)으로 구현한다. Spring AI는 필요할 때 확장 과제로 남긴다 |
| 결정자 | 본인 |

---

## 1. 배경

처음 받은 고도화 브리프는 같은 RAG를 두 번 구현하는 계획이었다.
1. Python(LangChain)으로 기본 RAG와 평가셋을 만든다.
2. 같은 RAG를 Spring Boot 4 + Spring AI 2.0으로 다시 구현한다.
3. Spring판에 Redis(캐시·대화 이력·사용량 제한), MCP 서버, 관측성을 붙인다.
4. 같은 평가셋으로 두 구현을 비교한다.

구현에 들어가기 전에, 이 프로젝트의 목적을 다시 정의했다.

- **목적:** 백엔드 개발자 포트폴리오. "어느 프레임워크가 나은가"를 증명하는 실험보다, **LLM 서비스를 운영 수준으로 만든 경험과 그 근거 수치**를 남기는 것이 중요하다.
- **핵심 과제:** ① 한국어 규정 문서의 **검색 정확도**를 끌어올리는 것, ② 캐시 등으로 **토큰 비용을 줄이는 것**.

이 목적에 비추어 두 프레임워크를 다시 검토했다.

---

## 2. 검토한 선택지

| 선택지 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 이중 구현 (브리프 원안) | 같은 RAG를 Python과 Spring AI로 각각 구현해 비교 | 두 프레임워크를 모두 다뤄 봄 | 같은 조건을 맞추는 작업(청크·임베딩·검색 결과 일치)에 시간이 많이 듦. Python에서 튜닝한 검색을 Java로 옮기기 어려움 |
| B. 혼합 구조 | Python이 검색·생성, Spring이 앞단(캐시·사용량 제한·관측성) | 실무에서 흔한 구조 | 서비스가 두 개라 1인 프로젝트로는 운영 부담이 큼. Spring AI 기능은 일부만 쓰게 됨 |
| **C. Python 단독 (채택)** | FastAPI + LangChain 1.x에 Redis·MCP·관측성까지 구현 | 정확도 튜닝과 운영 기능에 시간 집중 | Spring 경험이라는 차별점은 없음 |

---

## 3. 판단 기준

핵심 과제가 "한국어 검색 정확도"와 "토큰 비용 절감"이므로, 세 가지를 기준으로 삼았다.

1. 검색 고도화 도구를 **바로 쓸 수 있는가**
2. 새로운 기법을 **빨리 적용할 수 있는가**
3. 막혔을 때 **해결 자료가 충분한가**

---

## 4. 결정 근거

### 본인 판단 (요약)
1. **검색 고도화 기능이 Python에 훨씬 많다.**
2. **최신 기능이 Python에 먼저, 빠르게 나온다.**
3. **커뮤니티 규모가 크다.**

### 근거 ① 검색 고도화 기능
- **한국어 키워드 검색:** 형태소 분석기 Kiwi(`kiwipiepy`)는 Python 패키지다. Java 바인딩은 확인되지 않았다. Spring으로 한국어 하이브리드 검색(키워드 + 의미)을 하려면 한국어 토큰화 문제부터 따로 해결해야 한다.
- **고도화 기법:** BM25 하이브리드와 RRF 결합, MultiQuery, Decomposition, CrossEncoder 리랭커, 맥락 압축이 모두 Python 생태계에 있다. 학습 과정(LangChain 6개 섹션)의 실습 노트북으로 이미 직접 검증했다.
- **평가 도구:** 검색 지표(Hit Rate, MRR, NDCG)를 계산하는 krag, LLM-as-judge 평가기도 Python에 있다.
- **Spring AI와의 차이:** Spring AI 2.0의 RAG 구성은 벡터 검색과 Advisor(요청 앞뒤에 끼우는 부품) 중심이다. Python에서 튜닝한 하이브리드 검색과 리랭커를 쓰려면 Java로 다시 구현해야 하고, 옮기지 못하면 Spring판의 정확도가 Python판보다 떨어진다.

### 근거 ② 최신 기능 반영 속도와 프레임워크 성숙도
- **Spring AI는 신생이다.** 2.0 GA가 2026년 6월이고, 조사 시점(2026년 10월)에 이미 2.1.0-RC1이 나와 있었다. 2.0에서 설정 키와 모듈 이름이 다수 바뀌어 API 변화가 잦다.
- **문서와 실제 코드가 다른 부분을 직접 확인했다.** Spring AI 2.0.2 기준 조사에서 다음을 발견했다.
  1. 문서에 나온 Redis 시맨틱 캐시 스타터(`spring-ai-starter-vector-store-redis-semantic-cache`)가 Maven Central에 존재하지 않는다.
  2. MCP 서버 전송 방식의 기본값이 문서 설명과 다르다. `spring.ai.mcp.server.protocol=STREAMABLE`을 명시하지 않으면 deprecated된 SSE 방식이 켜진다.
  3. Prometheus 지표 이름이 문서 표와 실제 코드에서 다르다(예: ChatClient 지표).
- **왜 중요한가:** 신생 프레임워크로 학습과 튜닝을 하면, 문제가 생겼을 때 **원인이 내 코드인지 프레임워크인지** 가르는 데 시간이 많이 든다. 정확도 튜닝처럼 반복 실험이 많은 작업에는 안정적이고 자료가 많은 쪽이 유리하다.

### 근거 ③ 커뮤니티 규모
- LLM 애플리케이션 예제, 튜토리얼, 이슈 해결 자료는 Python 쪽이 압도적으로 많다.
- (정량 근거를 넣는다면: LangChain과 Spring AI의 GitHub 스타 수, PyPI·Maven 다운로드 수 비교. 아직 확인하지 않음)

### 근거 ④ 프로젝트 조건
- **기존 자산이 Python에 있다.** LangChain 학습(6개 섹션)과 실습, 이미 동작을 확인한 설정·모델 계층(로컬 임베딩 bge-m3, OpenAI·Claude 전환)을 그대로 이어서 쓸 수 있다.
- **1인 프로젝트의 시간 배분:** 두 구현을 같은 조건으로 맞추는 작업(청크 파일 공유, 공용 임베딩 서버, 검색 결과 일치 검증)에 들어갈 시간을, 정확도 튜닝과 운영 기능에 쓸 수 있다.

## 5. 포기한 것과 대응 (트레이드오프)

| 포기한 것 | 대응 |
|---|---|
| Java/Spring 백엔드 공고에서 "Spring에 LLM을 붙여 봤다"는 차별점 | 백엔드 역량의 핵심인 캐시 키 설계, 원자적 사용량 제한, SSE 스트리밍, 관측성, MCP 서버는 Python에서도 그대로 구현해 보여줄 수 있다 |
| Spring AI가 기본 제공하는 관측 지표(토큰 사용량 등) | Python에서는 메트릭 이름·라벨·버킷을 직접 설계해 구현한다. 이 자체가 설계 경험이 된다 |
| 두 프레임워크의 정량 비교 | 단계별 전후 비교로 대체한다. 예: 튜닝 전후 Hit@k, 캐시 적용 전후 토큰·지연·비용 |

---

## 6. 다시 검토할 조건

- Java 백엔드 직무 지원이 확정되거나, 회사의 Spring 시스템과 연동할 일이 생기면 → 혼합 구조(B)로 Spring 앞단을 확장 과제로 추가한다.
- Spring AI 2.x가 안정화되어 문서와 코드가 일치하고, 한국어 하이브리드 검색을 할 방법이 생기면 → 재검토한다.

---

## 7. 이 결정으로 바뀐 계획

| 구분 | 변경 전 (브리프) | 변경 후 |
|---|---|---|
| 구현 | Python + Spring AI 두 벌 | Python 하나 (FastAPI + LangChain 1.x) |
| 임베딩 | 두 구현이 같은 임베딩 서버(TEI)를 공유 | 이미 동작하는 로컬 bge-m3를 그대로 사용 |
| Redis·MCP·관측성 | Spring판에 구현 | Python판에 구현 |
| 비교 방식 | 두 구현의 비교표 | 단계별 전후 수치 비교 |
| 단계 | 1 Python 정리 → 2 Spring 재구현 → 3 Redis → 4 MCP → 5 관측성 → 6 비교 | 1 기본 RAG·평가 기준선 → 2 정확도 튜닝 → 3 토큰 절감(Redis) → 4 MCP → 5 관측성 → 6 결과 정리 |
