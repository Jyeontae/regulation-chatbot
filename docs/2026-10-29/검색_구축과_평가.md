## 요약

조문 단위로 나눈 청크 1,000개를 로컬 임베딩(`bge-m3`)으로 Chroma에 색인하고, 검색 결과만 근거로 답하는 LangChain 체인을 만들었다. 직원 질문 50개로 검색 평가셋을 만들어 기준선을 측정했다.

| 지표 (k = 4) | 결과 |
|---|---:|
| Hit@4 (LLM에 넘기는 4개 안에 정답이 있는 비율) | **0.89** |
| Recall@4 (필요한 정답 조문 중 가져온 비율) | 0.80 |
| MRR@10 (정답 순위 점수) | 0.76 |

규정 원문을 AI 도구에 넣을 수 없는 보안 제약 아래에서, 모든 스크립트가 **점수·개수·번호만** 출력하도록 설계해 원문을 보지 않고 평가와 원인 분석을 진행했다.

## 1. 구축한 것

```
chunks.jsonl ──build_index.py──► Chroma (cosine) ──search.py──► 상위 k개 조문 ──rag.py──► LLM 답변 + 근거 조항
 (청크 1,000)    bge-m3 로컬 임베딩                    유사도 순위            (--answer, 외부 API)
                                     └──eval_retrieval.py──► Hit@k · Recall@k · MRR
```

| 구성 | 설계 |
|---|---|
| 색인 (`build_index.py`) | 실행할 때마다 컬렉션을 비우고 전체를 다시 적재한다. 분할에서 사라진 청크가 검색에 남지 않게 하기 위해서다. 청크 id는 사람이 읽을 수 있는 chunkId(`카테고리/규정명#제5조-2`)를 그대로 쓴다 |
| 거리 함수 | cosine. 컬렉션 생성 시에만 적용되므로 저장소 여는 코드를 한곳(`vectorstore.py`)에 모아 색인과 검색이 같은 설정을 쓰게 했다 |
| 검색 확인 (`search.py`) | 기본 출력은 순위·카테고리·조 위치·유사도만. 규정명·본문은 옵션(`--show-names`, `--show-text`)으로 본인만 확인한다 |
| 답변 체인 (`rag.py`) | `prompt \| llm \| parser`. 발췌에 없는 내용은 "해당 규정을 찾을 수 없습니다"로 답하고, 마지막 줄에 근거 조항을 모두 적게 했다. 조 번호를 지어내지 않도록 머리말에 적힌 위치만 쓰게 했다 |
| 외부 전송 통제 | 답변 생성(`--answer`)만 외부 API로 조문을 보낸다. LangSmith 추적이 켜져 있으면 실행을 막는다. 체인 입력이 추적 서버에도 저장되기 때문이다 |

## 2. 검색 평가 설계

### 왜 검색부터 평가하나

RAG의 답은 검색이 가져온 조문을 넘지 못한다. 정답 조문이 LLM에 전달되지 않으면 프롬프트를 아무리 고쳐도 맞는 답이 나오지 않는다. 그래서 LLM 없이 검색만 따로 채점했다. 외부 전송이 없어서 보안 승인 없이 바로 돌릴 수 있다는 장점도 있다.

### 평가셋

| 항목 | 내용 |
|---|---|
| 형식 | 마크다운 표: id · 유형 · 질문 · 정답 section_id · 기대 답 |
| 규모 | 50문항 (정답 있음 45, 규정에 없음 5) |
| 유형 | 단순 사실 20, 조건 판단 10, 여러 조항 8, 구어체 7, 규정에 없음 5 |
| 작성 | 질문 초안은 일반적인 회사 규정 주제로 만들고, 정답 조문은 담당자가 규정을 보고 직접 채웠다 |
| 보관 | 질문·정답에 규정 내용이 들어가므로 git 제외 폴더에 두고, 양식만 git에 둔다 |

정답은 청크가 아니라 **조문(section_id)** 단위로 매겼다. 긴 조문은 여러 청크로 나뉘는데, 어느 조각이 걸리든 같은 조문을 찾은 것으로 봐야 하기 때문이다.

### 지표

| 지표 | 묻는 것 | 예 |
|---|---|---|
| Hit@k | 상위 k개 안에 정답이 하나라도 있나 | 정답 2개 중 1개만 찾아도 1 |
| Recall@k | 필요한 정답 조문을 다 가져왔나 | 정답 2개 중 1개만 찾으면 0.5 |
| MRR | 정답이 몇 등에 처음 나왔나 | 1등 1.0, 2등 0.5, 4등 0.25, 못 찾음 0 |
| 1등 유사도 | 규정에 없는 질문이 확실히 낮게 나오나 | 낮게 갈리면 LLM 호출 전 거절 기준으로 쓴다 |

k = 4를 기준으로 봤다. 실제로 LLM에 넘기는 조문 수(`RETRIEVER_K=4`)라서, 5등에 있는 정답은 LLM이 보지 못한다.

### 보안 제약 속에서 평가하는 방법

- 화면에는 점수와 질문 id만 출력한다. 질문 문장과 규정명은 나오지 않는다.
- 질문별 상세 결과(검색된 section_id, 유사도)는 로컬 CSV에만 남긴다.
- 정답 표기 오류는 `[제외] 정답 section_id 가 인덱스에 없음`에 질문 id로 알려 준다. 내용을 보지 않고도 어느 질문을 고칠지 알 수 있다.

## 3. 트러블슈팅: 첫 평가에서 39문항이 빠짐

| 항목 | 내용 |
|---|---|
| 증상 | 50문항 중 39문항이 "정답 section_id가 인덱스에 없음"으로 제외됨. 남은 11문항으로는 점수를 믿을 수 없음 |
| 확인 | 인덱스의 조문 수(125개)와 `chunks.jsonl`의 조문 수(937개, 문서 45개)를 비교. 개수만 세서 원문은 보지 않음 |
| 원인 | 분할 규칙을 고쳐 `chunks.jsonl`을 다시 만든 뒤, 인덱스를 다시 만들지 않았음. 평가셋 정답은 새 분할 기준으로 적혀 있었음 |
| 조치 | `build_index.py` 재실행 → 937개 조문, 50문항 전부 평가에 포함 |
| 교훈 | 분할과 색인은 따로 실행되므로 둘이 어긋날 수 있다. 평가 스크립트가 정답 id를 인덱스와 대조하는 검사를 갖고 있어서 점수를 잘못 믿기 전에 잡아냈다 |

## 4. 기준선 v0 결과

| k | Hit@k | Recall@k |
|---:|---:|---:|
| 1 | 0.67 | 0.48 |
| 3 | 0.84 | 0.72 |
| **4** | **0.89** | **0.80** |
| 5 | 0.89 | 0.81 |
| 10 | 0.91 | 0.87 |

| 유형 (k = 4) | 질문 | Hit@4 | Recall@4 | MRR |
|---|---:|---:|---:|---:|
| 단순 사실 | 20 | 0.90 | 0.88 | 0.82 |
| 조건 판단 | 10 | 0.90 | 0.90 | 0.59 |
| 여러 조항 | 8 | 1.00 | 0.69 | 0.94 |
| 구어체 | 7 | 0.71 | 0.57 | 0.63 |

| 1등 유사도 | 평균 | 최소 | 최대 |
|---|---:|---:|---:|
| 정답 있는 질문 (45) | 0.680 | 0.558 | 0.779 |
| 규정에 없는 질문 (5) | 0.558 | 0.497 | 0.628 |

### 해석

1. **찾는 능력보다 순위가 약하다.** k를 4에서 10으로 늘려도 Hit가 0.89에서 0.91로 거의 오르지 않는다. 못 찾는 질문은 더 많이 가져와서 해결되지 않는다.
2. **여러 조항 질문은 근거를 일부만 가져온다.** Hit@4 1.00에 비해 Recall@4가 0.69다.
3. **조건 판단은 정답이 1등이 아닌 경우가 많다.** Hit@4 0.90에 비해 MRR이 0.59다.
4. **구어체가 가장 약하다.** 다만 7문항이라 추세로 보기는 이르다.
5. **유사도로 미리 거절할 수 없다.** 두 분포가 0.558~0.628 구간에서 겹친다.

## 5. 운영 관점의 위험 분석

점수가 아니라 "틀렸을 때 사용자가 알아챌 수 있는가"를 기준으로 우선순위를 다시 매겼다.

| 순위 | 문제 | 근거 | 사용자에게 생기는 일 |
|---|---|---|---|
| 1 | 정답을 못 찾고, 못 찾은 것도 감지하지 못함 | Hit@4 0.89, 1등 유사도 분포 겹침 | 비슷한 다른 조문을 근거로 자신 있게 틀린 답 |
| 2 | 반쪽 근거 | 여러 조항 Recall@4 0.69 | 원칙만 찾고 예외·단서가 빠진 단정적인 답 |
| 3 | 옛 판본 혼입 | 중복 점검에서 다른 판본 의심 문서 발견 (6장) | 이미 바뀐 규정으로 답. 지표에는 정답으로 잡힐 수 있음 |
| 참고 | 구어체 약함 | 구어체 Hit@4 0.71, 평가셋 비중 16% | 실제 사용자 질문은 구어체가 많아 운영 점수가 평가보다 낮을 수 있음 |

근거 조항을 적게 하는 프롬프트만으로는 1순위를 막지 못한다. 검색이 실패하면 LLM은 **실제로 있는** 비슷한 조문을 근거로 붙이기 때문이다. 그래서 프롬프트, 인용 검증(답에 적힌 조문이 전달한 조문 안에 있는지), 화면에 근거 원문 함께 표시, 검색 개선을 겹쳐 쓰는 방향으로 정리했다.

## 6. 튜닝 준비

### 실험 규칙

| 규칙 | 이유 |
|---|---|
| 한 실험에서 하나만 바꾼다 | 점수 변화의 원인을 하나로 설명하기 위해 |
| 평가셋과 청크 파일의 지문(SHA-256 앞 12자리)을 기록한다 | 같은 시험지로 비교했는지 확인하기 위해 |
| 기준선 청크를 스냅샷으로 보관한다 | 데이터가 바뀐 뒤에도 v0을 다시 잴 수 있게 |
| 보류 평가셋(20문항)은 기준선과 마지막에만 잰다 | 튜닝용 평가셋에만 맞춘 개선(과적합)을 걸러내기 위해 |
| 0.05 미만의 변화는 차이로 보지 않는다 | 정답 있는 질문 45개라 한 문제가 약 0.02다 |

### 중복 문서 점검

문서끼리 본문을 5글자 조각으로 나눠 겹침 비율을 계산했다(`compare_docs.py`). 원문 대신 비율만 출력한다.

- 45개 문서, 990쌍 중 겹침 50% 이상 **9쌍**
- 통째로 같은 문서 1쌍: 조문 40개 중 37개가 글자까지 같고, 위치는 40개 모두 같음
- 작은 문서가 큰 문서 안에 들어 있는 쌍: 별지·발췌를 따로 뺀 파일로 추정
- 다른 판본 의심 3쌍: 둘째 문서에만 조 제목 인식 실패, 같은 조 번호 재등장 같은 분할 이상이 몰려 있음. 옛 조문과 새 조문을 나란히 놓은 대비표라면 증상이 모두 설명된다. 분할 단계에서 "분할 규칙 문제"로 기록했던 이상 일부가 사실은 "색인하지 말아야 할 문서" 문제일 수 있다는 것을 발견했다

### 개선 후보

| 약점 | 처방 | 오를 지표 |
|---|---|---|
| 같은 내용이 4칸을 나눠 차지함 | 중복·옛 판본 문서 제외 | Recall, Hit@4 |
| 긴 조문의 조각들이 4칸을 나눠 차지함 | 넉넉히 검색한 뒤 같은 조문 조각을 묶어서 4개 선택 | Recall |
| 정답이 2~3등에 머묾 | 리랭커 (`bge-reranker-v2-m3`, 로컬) | Hit@1, MRR |
| 구어체 | 일상어-규정 용어 사전 | 구어체 Hit |
| 정확한 용어 질문의 순위 | 하이브리드 검색 (Kiwi 형태소 분석 + BM25) | MRR |

형태소 분석 후 벡터에 저장하는 방법은 제외했다. `bge-m3`는 자연스러운 문장으로 학습되어 있어 미리 잘라 넣으면 오히려 불리하고, 구어체 문제는 단어를 쪼개는 문제가 아니라 다른 말로 묻는 문제라서 효과가 없다.

## 7. 배운 점

1. **점수보다 먼저 측정 자체를 의심한다.** 첫 실행의 낮은 점수는 검색 성능이 아니라 인덱스와 청크 파일의 불일치 때문이었다. 몇 문항이 실제로 채점됐는지부터 확인하는 습관이 필요하다.
2. **지표는 서로 다른 약점을 보여 준다.** Hit만 보면 여러 조항 유형이 만점이었지만, Recall은 근거가 빠진다는 것을, MRR은 순위가 약하다는 것을 보여 줬다.
3. **k를 늘리는 것은 답이 아니다.** k를 10까지 늘려도 거의 오르지 않았고, LLM에 보내는 조문(외부 전송량)만 늘어난다.
4. **운영 위험은 지표 순위와 다르다.** 운영에서는 1등 적중률보다 "실패를 감지할 수 있는가"와 "옛 규정으로 답하지 않는가"가 더 중요했다.
5. **데이터 품질 문제는 검색 단계에서 드러난다.** 분할 지표로는 "규칙대로 잘렸다"까지만 알 수 있었고, 중복·판본 문제는 검색과 중복 점검에서 보였다.
6. **보안 제약이 도구를 만든다.** 원문을 볼 수 없어서 만든 집계 출력, 정답 id 대조, 겹침 비율 계산이 그대로 품질 관리 도구가 되었다.

## 부록. 포트폴리오·이력서용 요약

- 사내 규정 RAG 챗봇의 검색 단계를 구축하고, 50문항 평가셋과 Hit@k·Recall@k·MRR 평가 파이프라인을 설계해 기준선 Hit@4 0.89를 측정
- 평가셋 정답 id를 인덱스와 대조하는 검사로 색인 누락(조문 937개 중 125개만 색인)을 발견해 해결
- 유형별 지표 분석으로 "찾기는 되지만 순위와 다중 근거가 약하다"는 약점을 특정하고, 운영 위험(근거 오인용, 예외 조항 누락, 옛 판본 혼입) 기준으로 개선 우선순위 수립
- 원문 열람이 불가능한 보안 제약 아래에서 집계 수치만 출력하는 평가·중복 점검 도구를 설계하고, 문서 45개 중 중복·판본 의심 9쌍을 찾음
