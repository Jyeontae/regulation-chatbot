# 검색 튜닝 실험 기록

검색 평가(`scripts/eval_retrieval.py`)로 기준선을 잡고, 한 번에 하나씩 바꿔 가며 효과를 잰 기록이다.
이 문서에는 집계 점수와 질문 id만 적는다. 질문·정답·규정명은 `data/eval/`(git 제외)에만 둔다.

## 1. 실험 규칙

| 규칙 | 이유 |
|---|---|
| 한 실험에서 하나만 바꾼다 | 점수가 바뀐 원인을 하나로 설명하기 위해 |
| 평가셋은 고정한다. 바꾸면 지문을 새로 적고 기준선부터 다시 잰다 | 평가셋이 바뀌면 전후 점수를 비교할 수 없다 |
| 보류 평가셋은 기준선과 마지막에만 잰다 | 튜닝용 평가셋에만 맞춘 개선(과적합)을 걸러내기 위해 |
| 0.05 미만의 변화는 차이로 보지 않는다 | 정답 있는 질문이 45개라 한 문제가 약 0.02다 |
| 개선 판단은 Hit@4를 먼저 본다 | LLM에 넘기는 조문이 4개(`RETRIEVER_K=4`)다 |

지문은 파일 SHA-256의 앞 12자리다. PowerShell에서 `Get-FileHash <파일>`로 구한다.

### 보류 평가셋

- 파일: `data/eval/holdout_set.md` (git 제외). 20문항, id는 `H01`부터 시작한다.
- 유형 분포: 단순 사실 8, 조건 판단 4, 여러 조항 3, 구어체 3, 규정에 없음 2.
- 정답을 다 채운 뒤 지문을 이 문서에 적고, 그 뒤로는 고치지 않는다.
- 실행: `poetry run python scripts/eval_retrieval.py --eval-set data/eval/holdout_set.md`
- 튜닝 중에는 이 파일의 결과 CSV를 열지 않는다. 틀린 질문을 보고 고치면 보류셋이 튜닝용이 된다.

## 2. 기준선 v0 (2026-10-29)

### 조건

| 항목 | 값 |
|---|---|
| 분할 | 조문 단위, 1,000자 초과 조만 항 경계에서 다시 나눔 (`MAX_CHARS = 1000`) |
| 위치 머리말 | 있음 (`[카테고리 > 규정명 > 장 > 조]`) |
| 청크 / 조문(section_id) | 1,000개 / 937개, 문서 45개 |
| 임베딩 | `BAAI/bge-m3`, CPU |
| 벡터 저장소 | Chroma, cosine |
| 검색 | 벡터 검색만, k = 4 |
| 평가셋 | 50문항 (정답 있음 45 / 규정에 없음 5) |
| 유형 분포 | 단순 사실 20, 조건 판단 10, 여러 조항 8, 구어체 7, 규정에 없음 5 |
| 지문 | 평가셋 `a6644be4bc3c`, `chunks.jsonl` `15cf9114a400` |
| 상세 결과 | `data/eval/results/retrieval-20261029-151109.csv` (공유 금지) |
| 스냅샷 | `data/chunks/v0/chunks.jsonl` (지문 같음). 데이터 실험으로 `chunks.jsonl`이 바뀐 뒤에도 v0을 다시 잴 수 있게 남긴다 |

v0 인덱스가 다시 필요하면(보류셋 v0 측정, 평가셋 정답 수정 후 재채점) 스냅샷으로 별도 컬렉션을 만든다. 실험용 인덱스는 건드리지 않는다.

```powershell
$env:CHUNKS_PATH='data/chunks/v0/chunks.jsonl'; $env:CHROMA_COLLECTION='regulations_v0'
poetry run python scripts/build_index.py
poetry run python scripts/eval_retrieval.py --eval-set data/eval/holdout_set.md
Remove-Item Env:CHUNKS_PATH, Env:CHROMA_COLLECTION
```

### 결과

|---:|---:|---:|
| 1 | 0.67 | 0.48 |
| 3 | 0.84 | 0.72 |
| **4** | **0.89** | **0.80** |
| 5 | 0.89 | 0.81 |
| 10 | 0.91 | 0.87 |

MRR@10 = 0.76

| 유형 (k = 4) | 질문 | Hit@4 | Recall@4 | MRR |
|---|---:|---:|---:|---:|
| 단순 사실 | 20 | 0.90 | 0.88 | 0.82 |
| 조건 판단 | 10 | 0.90 | 0.90 | 0.59 |
| 여러 조항 | 8 | 1.00 | 0.69 | 0.94 |
| 구어체 | 7 | 0.71 | 0.57 | 0.63 |

| 1등 유사도 | 평균 | 최소 | 최대 |
|---|---:|---:|---:|
| 정답 있는 질문 (45) | 0.680 | 0.558 | 0.779 |
| 규정에 없는 질문 (5) | 0.558 | 0.497 | 0.628 |

개선할 질문

- 상위 10개 안에 정답 없음: Q03, Q04, Q27, Q43
- 정답이 4위 밖: Q40 (6위)

### 해석

1. **찾기보다 순위가 약하다.** k를 4에서 10으로 늘려도 Hit가 0.89에서 0.91로 거의 오르지 않는다. 못 찾는 질문은 k를 늘려서 해결되지 않는다.
2. **여러 조항은 일부만 찾는다.** Hit@4는 1.00이지만 Recall@4가 0.69다. 필요한 조문 중 일부만 LLM에 넘어간다.
3. **조건 판단은 정답이 1등이 아닌 경우가 많다.** Hit@4 0.90에 비해 MRR이 0.59다.
4. **구어체가 가장 약하다.** 7문항 중 2개를 놓쳤다. 문항 수가 적어 추세로 보기는 이르다.
5. **유사도로 미리 거절할 수 없다.** 두 분포가 겹친다(정답 있는 질문 최소 0.558 < 규정에 없는 질문 최대 0.628).

### 기준선을 잡기 전에 걸러진 문제

처음 실행에서는 50문항 중 39문항이 "정답 section_id가 인덱스에 없음"으로 빠졌다. 인덱스에는 조문이 125개였고 `chunks.jsonl`에는 937개였다. 분할을 다시 한 뒤 인덱스를 다시 만들지 않은 것이 원인이었다. `build_index.py`를 다시 실행하자 50문항이 모두 평가에 들어갔다. 평가 스크립트의 `[제외]` 출력이 데이터 불일치를 잡아낸 사례다.

## 3. 실험 후보

데이터 개선을 먼저 하고, 모델 쪽 개선은 그 뒤에 한다. 데이터 개선 후보는 [분할 구현 기록 11장](../2026-10-28/split_chunk_구현기록.md)에서 가져왔다.

| id | 바꾸는 것 | 가설 | 볼 지표 |
|---|---|---|---|
| D1 | 중복 문서 정리 | 같은 규정이 두 카테고리에 있으면 상위 4칸을 중복이 차지한다 | Hit@4, 여러 조항 Recall@4 |
| D2 | 조 제목 인식 보완 | 여러 조가 한 청크로 합쳐진 문서를 조 단위로 나누면 해당 조문의 순위가 오른다 | Hit@1, 개선할 질문 |
| D3 | 본문 손실 문서 보완 | 목차로 잘못 판단해 버린 조문을 살리면 그 조문을 찾는다 | 개선할 질문 |
| D4 | 합본 문서 분리 | 규정명 머리말이 정확해지면 규정을 헷갈리지 않는다 | Hit@4 |
| D5 | 짧은 청크(50자 미만) 처리 | 짧은 조문은 벡터가 부정확해 순위를 어지럽힌다 | MRR |
| D6 | 위치 머리말 제거 (대조 실험) | 머리말이 검색에 기여한다면 빼면 점수가 떨어진다 | 전체 |
| M1 | 리랭커 (`bge-reranker-v2-m3`, 로컬) | 후보를 다시 줄 세우면 1등이 정확해진다 | Hit@1, 조건 판단 MRR |
| M2 | 구어체 용어 사전 | 질문의 일상어를 규정 용어로 보완하면 구어체를 찾는다 | 구어체 Hit@4 |
| M3 | 하이브리드 검색 (Kiwi + BM25) | 정확한 용어·조문 번호 질문의 순위가 오른다 | 단순 사실 MRR |

## 4. D1 중복 문서 정리

### 절차

문서 번호(#01~)는 `data/raw` 파일 순서로 매기므로 파일을 옮기면 뒤 번호가 당겨진다. 1~3단계의 번호는 옮기기 전에 기록한다.

1. 겹치는 문서 쌍을 찾는다. 겹침 50% 이상인 쌍이 나온다.
   `poetry run python scripts/compare_docs.py`
2. 쌍마다 조 단위로 비교한다. 출력 끝의 [판단 기준]으로 같은 규정, 개정 전후판, 포함 관계 중 무엇인지 가른다.
   `poetry run python scripts/compare_docs.py --pair A B`
   파일 이름은 `--show-names`로 본인만 확인한다.
3. 남길 문서를 정하고 아래 표에 번호로 적는다.
4. 평가셋에서 뺄 문서의 section_id를 지운다. 정답이 뺄 문서에만 있던 질문은 남길 문서의 같은 조문으로 바꾼다. 새 지문을 적는다.
5. 고친 평가셋으로 v0을 다시 채점한다(2장의 `regulations_v0` 컬렉션). 이 점수가 D1의 비교 기준이다.
6. 뺄 파일을 `data/excluded/`(git 제외)로 옮기고 `build_chunks.py` → `build_index.py` → `eval_retrieval.py` 순서로 실행한다.

5단계를 건너뛰면 점수 변화가 평가셋 수정 때문인지 중복 정리 때문인지 가를 수 없다.

관찰

- #05 ↔ #29를 빼면 모두 번호가 붙어 있다. 번호는 파일 이름 순서라, 이름이 비슷한 같은 계열 파일이다.
- 다른 판으로 의심되는 쌍(#22 ↔ #23, #38 ↔ #39, #34 ↔ #35)은 둘째 문서에 분할 이상이 몰려 있다. 대비표처럼 옛 조문과 새 조문이 나란히 있는 문서라면 조 제목이 표 안에 들어가 인식에 실패하고, 같은 조 번호가 두 번 나온다. 분할 구현 기록 11장의 1순위 문제(#23·#39 조 제목 인식 실패)와 5순위 문제(#35 id 보정)가 같은 원인일 수 있다.
