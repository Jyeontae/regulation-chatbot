## 1. 어제 실험 마무리: 리랭커 두 번째 검색어 세트

11-02 저녁에 세션이 끝나면서 기록하지 못한 2세트 결과다. 평가셋 50문항 기준이고, 시간은 리랭크만 잰 값(평균 / 느린 10%)이다.

|---|---|---:|---:|---:|---:|---:|---|
| 1 | 기준선 | 0.76 | 1.00 | 0.86 | 0.69 | – | – |
| 1 | 후보 5 + 원래 질문 | 0.80 | 1.00 | 0.90 | 0.69 | 2.1 / 2.8초 | 통과 |
| 1 | **후보 5 + 다듬은 검색어** | **0.89** | 1.00 | **0.93** | 0.76 | 2.1 / 2.7초 | 통과 |
| 1 | 후보 10 + 원래 질문 | 0.76 | 0.98 | 0.86 | 0.76 | 4.1 / 5.6초 | 예산 초과 |
| 1 | 후보 10 + 다듬은 검색어 | 0.84 | 0.98 | 0.90 | **0.92** | 3.5 / 4.5초 | Hit@4 지킴선 위반 |
| 1 | 후보 20 + 원래 질문 | 0.76 | 0.96 | 0.86 | 0.76 | 7.4 / 9.5초 | 예산 초과 |
| 2 | 기준선 | 0.73 | 0.98 | 0.84 | 0.69 | – | – |
| 2 | 후보 5 + 원래 질문 | 0.82 | 1.00 | 0.91 | 0.65 | 2.5 / 3.3초 | 통과 |
| 2 | **후보 5 + 다듬은 검색어** | 0.82 | 1.00 | 0.91 | 0.69 | 2.5 / 3.2초 | 통과 |
| 2 | 후보 10 + 원래 질문 | 0.78 | 0.98 | 0.87 | 0.72 | 4.7 / 6.7초 | 예산 초과 |

- **미리 정한 규칙의 결과:** 두 세트 모두 **후보 5개**가 뽑힌다. 입력은 다듬은 검색어가 원래 질문과 같거나 낫다.
- **확정은 보류한다.** 이 비교는 10-30에 Haiku가 다듬은 검색어 기준인데, 지금 채팅에서는 gpt-5.4-mini가 다듬는다. 리랭커 입력을 다듬은 검색어로 바꾸면 리랭크 품질이 아직 재지 않은 다듬기 품질에 묶이므로, OpenAI 검색어 세트로 한 번 더 비교한 뒤 확정한다(4절 B2). 지금 `chat.py`와 `eval_answers.py`는 원래 질문을 넣는다.
- **OpenAI 답변 재평가:** 실행되지 않았다(세션 종료로 중단).
- 후보 10개 + 다듬은 검색어는 여러 조항 Recall@4를 가장 많이 올리지만(0.81~0.92), 예산이나 지킴선을 넘는다. 리랭커가 빨라지면(4절 C5) 다시 볼 후보다.

## 2. 먼저 정해야 할 전제 (빠진 영역 점검의 '높음' 항목)

### 2.1 외부 전송 승인
- 승인 범위를 결정 문서에 적고 근거를 링크한다. 범위에는 수신처(OpenAI), 보내는 항목(질문, 질문 + 상위 4개 발췌, 평가 판정), 평가용 반복 전송 허용 여부, 보관 조건이 들어간다.
- OpenAI는 별도 승인(ZDR·MAM)이 없으면 악용 감시 로그를 **최대 30일** 보관한다 ([OpenAI: Your data](https://developers.openai.com/api/docs/guides/your-data), 검증됨).
- 승인을 확인하기 전에는 API가 필요한 작업(4절 단계 B, 보류셋 실행, 재판정)을 멈추고 API 없는 작업부터 한다.

### 2.2 규정·별표 단위 전송 등급
- 질문마다 외부로 나가는 양의 대부분은 상위 4개 발췌다. 보수표·수당표 같은 별표나, 서식에 적힌 담당자 연락처가 검색에 걸리면 그대로 나간다. 인원이 적은 직급의 보수표에서는 개인 급여를 거꾸로 계산할 수도 있다.
- 제안: 규정이나 별표 단위로 `external_ok` 메타데이터를 둔다. 제외 목록은 사람이 정하고 로컬에만 둔다. 제외 청크가 상위 4개에 들어오면 LLM에 보내지 않고 위치와 "원문 확인" 안내만 화면에 보여 준다. `chunks.jsonl`에서 개인정보 형태(주민번호·전화·이메일·계좌)가 들어 있는 청크 수를 유형별로 **집계만** 출력해 규모를 본다.

### 2.3 AI 개발 도구를 거쳐 나가는 경로
- Claude Code, Codex, 워크플로 하위 에이전트가 읽은 파일과 실행 출력은 그 도구의 공급자에게 전송된다. 지금 "`data/`는 열지 않는다"는 규칙은 메모와 지시로만 지켜진다.
- 제안(설정 변경이라 사용자 결정 필요): 프로젝트 `.claude/settings.json`의 권한 거부 규칙으로 `data/**`와 `.env`의 읽기·검색·수정을 막는다. 규정 이름이나 본문을 보여 주는 스크립트 옵션(`--show-names`, `--show-text`)은 대화형 터미널에서 환경 변수를 켰을 때만 동작하게 스크립트 안에서 막는다.

### 2.4 질문 입력 최소화
- 질문 칸에 긴 문서를 붙여 넣으면 그 전문이 다듬기와 답변 두 단계에서 외부로 간다. 개인정보 형식 마스킹(4절 E4)으로는 이를 막지 못한다.
- 제안: 질문 길이에 상한(예: 300자)을 두고 여러 줄 붙여넣기를 감지한다. "안녕", "고마워" 같은 잡담에는 LLM을 부르지 않고 로컬에서 답한다.

| C1 | 상위 4칸 중복 제거 (R08) | 같은 section_id 조각은 한 칸으로 치고, 머리말을 뺀 본문이 완전히 같은 청크는 하나만 남긴다. 비운 칸은 다음 순위의 다른 조문으로 채운다. 비교안으로 리랭커 점수 기반 MMR을 직접 구현한다(LangChain의 MMR 함수는 질의 임베딩 코사인을 쓰므로 그대로 쓰면 리랭커 점수가 반영되지 않는다). 노력이 적고 결과가 매번 같다 | 없음 |
| C2 | 검색어별 몫으로 후보 모으기 (R03) | 지금은 두 검색 결과를 최대 코사인으로 합치는데, 다듬은 검색어 쪽 점수가 대체로 높아 원래 질문이 찾은 조문이 밀린다. 원래 질문과 다듬은 검색어에서 각각 상위 3개를 가져와 합친다. 조정할 값이 m 하나라 과적합 위험이 작다 | 없음 |
| C3 | 질문 분해 (R04) | 다듬기 호출 한 번에서 하위 검색어 1~3개를 구조화 출력으로 받고, 하위 검색어마다 4칸 중 한 칸을 보장한다. 예제 005의 Decomposition에 해당하며 한 번도 시도하지 않았다 ([arXiv 2507.00355](https://arxiv.org/abs/2507.00355)) | 다듬기 출력 토큰만 수십 개 늘어난다 |
| C4 | 본문 속 참조 따라가기 (R11) | 분할기가 이미 만드는 `refs` 메타데이터(`제3조`, `별표 1`)로, 상위 1~2개 조문이 가리키는 같은 규정의 조문을 리랭크 후보에 더한다. 원칙 조문이 가리키는 예외·정의·금액표는 질문과 겹치는 단어가 적어 벡터 검색으로 잘 안 올라온다 ([arXiv 2604.06173](https://arxiv.org/abs/2604.06173)) | 없음 (메타데이터 조회) |
| C5 | 리랭커 교체·가속 (R02) | [nlpai-lab/KURE-Reranker-nano](https://huggingface.co/nlpai-lab/KURE-Reranker-nano)를 시험한다. 149M, Apache-2.0, 최대 8,192토큰이고, 카드 자체 보고로 한국어 평균 nDCG@10 0.8757(bge-reranker-v2-m3 0.8518), 법령 세트(LawIRKo) 0.8368(0.7906)이다(검증됨). **CPU 속도는 공개되지 않았다.** 행렬곱 파라미터 비는 약 0.36이라 실제로 얼마나 빨라지는지 직접 재야 한다. `RERANKER_MODEL`만 바꾸면 되므로 코드는 그대로다. 품질에서 밀리면 지금 모델을 int8로 가속한다. torch의 동적 양자화는 제거 예정 API라 비교용으로만 쓰고, ONNX int8은 별도 가상환경에서 내보낸다(optimum 계열은 설치된 transformers 5.21과 충돌) ([Sentence Transformers 효율화 문서](https://sbert.net/docs/cross_encoder/usage/efficiency.html)) | 없음. 모델 다운로드(약 0.1B) 승인 필요 |

### 단계 D — 평가셋 확장

| # | 할 일 | 내용 |
|---|---|---|
| D1 | 보류셋 채우기 (R05①) | 20문항의 정답 section_id와 기대 답을 사람이 채운다. 챗봇 답으로 초안을 잡으면 평가가 순환된다. **단계 C보다 먼저** 정답 section_id만이라도 채워야 C의 결과를 확인할 수 있다. 10-30에 AI가 바꾼 정답 4문항(Q03·Q04·Q27·Q32)도 이때 검수한다 |
| D2 | 기대 답을 핵심 사실 목록으로 (R05②) | 기대 답 옆에 '핵심 사실' 1~5개(금액·기한·대상·조건, 사실마다 근거 section_id)를 적고, 사실마다 포함/누락/모순을 판정한다. 여러 조항 답에서 어느 조문의 사실이 빠졌는지가 검색 Recall과 바로 연결된다 ([arXiv 2403.18771](https://arxiv.org/abs/2403.18771)) |
| D3 | 여러 조항 문항 늘리기 (R05③) | 지금 8개라 1문항이 0.125다. 평가셋과 보류셋을 합쳐 15~20개 이상으로 늘린다 |
| D4 | 부정 예시 20~30개 | 규정에 없는 질문이 5개뿐이고 "주제 자체가 없음"과 "세부가 없음"이 구분돼 있지 않다. 근접 질문(표에 없는 직급·경우), 법령에 위임된 사항, 다른 시점, 표 조회 유형을 넣는다. 거절 지표도 "규정에 없는데 답한 비율(위험)"과 "정답 있는데 거절한 비율"로 나눈다 |
| D5 | 사람 보정 라벨 (R07③) | 현재 설정의 답변 45개에 통과/실패와 한 줄 이유를 단다. 판정자와의 일치는 실패 검출률·통과 검출률이나 Cohen's kappa로 본다 ([Hamel Husain, LLM judge](https://hamel.dev/blog/posts/llm-judge/)) |
| D6 | 실사용 질문 | 동료 5~10명에게 질문 문장만 받아 30~50문항의 실사용 세트를 만들고, 사내 약어·은어 사전도 뽑는다 |
| D7 | 과적합 관리 | 보류셋은 "큰 하락을 잡는 회귀 점검"으로만 쓰고 사용 횟수를 기록한다. 결정마다 비교할 설정 수를 미리 2~3개로 정한다 |

### 운영

- **모델 고정:** 임베딩·리랭커의 revision(커밋 해시)을 `.env`와 manifest에 남긴다. 새 모델은 safetensors 형식이고 원격 코드 실행 없이 로드될 때만 쓴다. `poetry.lock`을 커밋한다.
- **로컬 자료 보호:** 디스크 암호화(BitLocker) 여부와 `data/`가 동기화 폴더 밖인지 `check_setup.py`로 확인한다. 사람이 단 라벨만 승인된 곳에 백업하고, 결과 CSV는 보관 기간을 둔다.
- **실행 중 외부 연결 실측:** 채팅 한 번과 평가 한 번 동안 프로세스의 원격 연결을 기록해 허용 목록(OpenAI API, 모델 받을 때만 Hugging Face)과 비교한다. 의존성을 올린 뒤에도 다시 돌린다.
- **개정 반영 절차와 라벨 무효화 감지:** 평가셋 정답마다 조문 본문 해시를 저장해 두고, 재색인 때 해시가 바뀐 문항은 "재검수 필요"로 빼고 manifest에 남긴다.
- **목표치와 종료 조건:** 파일럿 진입 기준을 미리 적는다(예: 전송 승인 완료, 규정에 없는데 답한 비율, 여러 조항 판정, 정답 인용, 전체 p90, 근거 원문 보기와 피드백 구현). 기준을 채우면 튜닝을 멈추고 소수 사용자 파일럿으로 넘어간다. 구체적인 값은 사용자가 정한다.

## 7. 하지 않는 것이 좋은 것

| 항목 | 이유 |
|---|---|
| 하이브리드 BM25·학습형 희소 검색 재도입 | 10-30에 기각됨 (전체 Hit@4 0.96 → 0.89, 구어체 하락) |
| 유사도·리랭커 점수 문턱으로 미리 거절 | 분포가 겹치고 규정에 없는 질문이 5개뿐이라 기준을 정할 수 없음 (D4로 부정 예시를 늘린 뒤 재검토) |
| LLM으로 순위 매기기·압축·맥락 만들기 | 후보나 문서 전체의 본문을 외부 LLM에 추가로 보내야 하고, 호출마다 수 초 증가. 압축은 "금액은 원문 그대로" 규칙과 충돌 |
| 의미 단위 분할·고정 길이 분할로 교체 | 조·항 단위가 뚜렷하고, 바꾸면 section_id 평가와 조문 인용이 흐려짐 |
| 외부 임베딩·번역 | 규정 전체가 새 수신처로 나감 |
| 임베딩 모델 교체를 지금 진행 | Hit@4가 약 1.00이라 병목이 1차 검색이 아님. 재색인과 전체 재평가 비용 |
| 이 노트북에서 로컬 LLM으로 실시간 답변 | GPU가 없고, 메모리가 32GB 단일 모듈(4000MHz로 동작 중일 가능성)이라 답변에 수십 초 예상 |
| 답변 캐시(정확·시맨틱) | 사용자가 사실상 한 명이라 적중률이 낮고, "정규직/계약직"처럼 한 단어로 답이 바뀌어 시맨틱 캐시는 위험 |
| RAGAS·DeepEval 같은 평가 프레임워크 도입 | 텔레메트리가 기본으로 켜져 있고 의존성이 크며 영어 프롬프트. 설계만 빌려 쓴다 |
| 외부 LLM으로 청크 기반 합성 질문 만들기 | 규정 본문이 문서화되지 않은 경로로 나감 |
| 다른 공급자로 자동 폴백 | 장애 때 사용자가 고르지 않은 수신처로 자동 전송됨. 타임아웃·재시도만 둔다 |
| "일부 못 찾음"이면 자동 보충 검색 후 재답변 | 답변 호출이 두 번이 되어 3~5초 늘고 넘기는 발췌가 4개를 넘음. C의 결과를 본 뒤 재검토 |
| 별표 표 구조 보존 재분할, HWP 직접 읽기 | 표 조회 질문의 오답 규모를 아직 모름. 한글 원본이 있는지부터 집계 |
| FastAPI·SSO·컨테이너 배포 | 승인과 배포 결정 전에는 과투자 |
| LangSmith 추적, FAISS | 추적은 본문을 외부로 보냄. FAISS는 이 규모에서 이득 없음 |
| 더 싼 소형 모델로 지금 교체 | gpt-5.4-mini 답변 비용은 이미 질문당 약 0.3~0.4센트(추론 토큰 제외 추정). 품질 확인(B3)이 먼저 |

## 8. 검증에서 바로잡힌 내용
