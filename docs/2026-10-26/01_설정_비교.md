# 사내 규정 챗봇 — 설정 비교 (Phase 0)

전제: 규정 파일 형식 **PDF**, **새 프로젝트 폴더 + 최신 LangChain**으로 시작.
아래 항목별로 장단점을 비교하고, 마지막에 조합안 3가지(A/B/C) 중 하나를 고른다.

## ✅ 결정 사항 (2026-10-26)

| 항목 | 결정 | 비고 |
|---|---|---|
| 조합 | **B. 혼합** | 임베딩은 로컬, 답변 생성만 외부 API |
| 임베딩 | **`BAAI/bge-m3`** (HuggingFace, 로컬) | 최종 확정은 Phase 3 평가 후 (비교 후보: multilingual-e5-large) |
| LLM | **OpenAI API + Anthropic Claude API** | `.env`의 `LLM_PROVIDER=openai` / `anthropic`으로 전환, Phase 5에서 두 모델 품질 비교 |
| 모델명 | `.env`에서 지정 | OpenAI는 `gpt-5.4-mini-2026-03-17`(날짜 고정 스냅샷), Claude는 `claude-sonnet-5-5`(품질) / `claude-haiku-5-5`(비용) |

- 선택 이유: 규정 문서라 **전체를 외부로 보내는 C는 제외**. 하지만 **GPU가 없어** 로컬 LLM(A)은 답변 속도가 실사용 수준이 안 됨 → 임베딩(전체 문서를 다루는 부분)만 로컬, 답변 생성만 API인 B.
  - 임베딩은 CPU로도 충분: 인덱싱은 한 번만(규정 수천 청크 기준 수 분~수십 분), 질문 임베딩은 1건이라 빠름.
  - 추후 GPU 서버가 생기면 `.env`의 `LLM_PROVIDER=ollama`로 A 전환이 가능하도록 구조를 열어 둔다.
- 외부 전송 최소화 원칙: LLM에는 **상위 k개(3~5개) 조문만** 보내고, 문서 전체·파일 경로 등 불필요한 메타데이터는 보내지 않는다.
- 보안: 질문과 검색된 조문 몇 개가 OpenAI·Anthropic 서버로 전송됨 → 정보보안 담당자 확인 필요. 규정 전체(인덱싱)는 외부로 나가지 않음.
- API 키는 `.env`에만 두고 git에 올리지 않는다 (`.gitignore`).

## 1. 가장 큰 결정 — 데이터가 어디까지 나가는가

| 구성 | 임베딩 | 답변 LLM | 외부로 나가는 데이터 | 한 줄 평가 |
|---|---|---|---|---|
| **A. 전부 로컬** | bge-m3 (HuggingFace) | Ollama 로컬 모델 | 없음 | 보안 최상, 대신 PC 사양과 답변 품질이 관건 |
| **B. 혼합** | bge-m3 (로컬) | OpenAI / Claude 등 API | 질문 + 검색된 조문 3~5개 | 품질·속도 좋음, 조문 일부가 외부로 나감 |
| **C. 전부 외부** | OpenAI 임베딩 | OpenAI API | 규정 전체(인덱싱 시) + 질문 | 실습과 동일해 가장 쉬움, 규정 전체가 외부로 나감 |

> 이 결정은 기술이 아니라 **회사 보안 정책**의 문제다. 정보보안 담당자에게 "규정 문서를 외부 LLM API로 보내도 되는가"를 먼저 확인할 것.
> 어느 쪽이 될지 모르면 **설정값(.env) 하나로 A↔B↔C를 바꿀 수 있게** 만들어 두면 된다 (아래 추천안).

## 2. 임베딩 모델

| 모델 | 실행 | 한국어 | 비용 | 장점 | 단점 |
|---|---|---|---|---|---|
| `BAAI/bge-m3` (HF) | 로컬 | 좋음 | 무료 | 다국어·한국어 강함, 긴 입력 처리, 실습 004~006에서 계속 사용 | 첫 다운로드 약 2GB, CPU면 인덱싱이 다소 느림 |
| OpenAI `text-embedding-3-small` | API | 좋음 | 유료(저렴) | 설치 없음, 빠름, 품질 안정적 | 문서가 외부로 전송, 인터넷 필요 |
| Ollama `bge-m3` | 로컬 | 좋음 | 무료 | Ollama 하나로 임베딩·LLM 통합 관리 | Ollama 서버를 따로 띄워야 함 |
| Ollama `nomic-embed-text` | 로컬 | **약함** | 무료 | 가벼움 | 한국어 검색 품질 낮음 (섹션 3에서 확인) |

**정리:** 한국어 규정이면 **bge-m3**가 1순위. HF로 돌릴지 Ollama로 돌릴지는 LLM을 Ollama로 쓰는지에 따라 맞추면 된다.

## 3. 답변 생성 LLM

| 선택지 | 실행 | 한국어 답변 | 속도 | 비용 | 비고 |
|---|---|---|---|---|---|
| OpenAI 소형 모델 (실습: gpt-4o-mini) | API | 좋음 | 빠름 | 유료(저렴) | 실습 코드 그대로 활용 가능 |
| Anthropic Claude | API | 좋음 | 빠름 | 유료 | 긴 문맥, 지시 따르기 우수 |
| Google Gemini | API | 좋음 | 빠름 | 유료(무료 구간 있음) | |
| Groq | API | 모델에 따라 다름 | 매우 빠름 | 유료(무료 구간 있음) | 오픈소스 모델을 외부 서버에서 실행 → 외부 전송은 동일 |
| Ollama 로컬 (예: EXAONE·Qwen 계열 7~8B) | 로컬 | 보통~좋음 | **사양 의존** | 무료 | 외부 전송 없음. GPU 없으면 답변 하나에 수십 초 걸릴 수 있음 |

**로컬 LLM 체크 포인트**
- GPU(VRAM 8GB 이상)가 있으면 7~8B 모델은 실사용 가능한 속도.
- CPU만 있으면 개발·테스트는 가능하지만 여러 명이 동시에 쓰는 서비스로는 부족.
- 한국어 품질은 모델마다 차이가 크다 → Phase 5에서 평가셋으로 2~3개 비교해서 결정.

## 4. PDF 로더

| 로더 | 장점 | 단점 |
|---|---|---|
| `PyPDFLoader` (pypdf) | 실습에서 사용, 설치 간단 | **한글 PDF에서 띄어쓰기가 사라지는 경우가 있음** |
| `PyMuPDFLoader` (pymupdf) | 빠르고 한글 추출이 대체로 깔끔, 페이지 정보 유지 | 패키지 추가 설치 |
| Unstructured | 표·레이아웃 인식 | 무겁고 설치가 복잡 |

> 실제 사례: 이번에 강의 PDF(섹션 1·5)를 pypdf로 추출했더니 `섹션1:RAG와LangChain기초`처럼 **공백이 전부 붙어서** 나왔다.
> 띄어쓰기가 사라지면 BM25 키워드 검색과 정규식 분할(`제N조`) 둘 다 영향을 받는다.
> → **PyMuPDFLoader를 기본으로, 규정 PDF 몇 개로 두 로더 결과를 비교**해서 확정한다. 스캔본(이미지) PDF라면 OCR이 별도로 필요.

## 5. 분할 방식

| 방식 | 장점 | 단점 | 규정 적합도 |
|---|---|---|---|
| **정규식 (`제N장` / `제N조` / `①`)** | 조문 단위로 잘려 근거 인용이 정확, 메타데이터(조 번호) 추출 쉬움 | 규정마다 표기가 다르면 패턴 조정 필요 | ★★★ |
| Recursive (고정 길이) | 범용, 설정 간단 | 조문 중간이 잘림 | ★★ (긴 조문 2차 분할용) |
| Semantic Chunking | 의미 단위 분할 | 임베딩 비용, 결과 예측 어려움 | ★ |

**정리:** 정규식으로 조 단위 분할 → 너무 긴 조문만 Recursive로 2차 분할.

## 6. 벡터 저장소

| 저장소 | 장점 | 단점 |
|---|---|---|
| **Chroma** | 문서 추가·변경·삭제가 쉬움, metadata 필터, 로컬 파일로 저장 | 수백만 건 이상 대규모에는 불리 |
| FAISS | 매우 빠름, 대규모 적합 | 문서 변경이 불편, metadata 필터가 약함 |

**정리:** 규정 문서는 많아야 수천 청크 → 규모 문제 없음. **규정 개정 시 교체(삭제→추가)**가 잦으므로 **Chroma**.

## 7. 검색 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| 벡터 검색만 | 구어체 질문·동의어에 강함 | "경조금", "제12조" 같은 정확한 용어에 약할 수 있음 |
| BM25만 | 정확한 용어·조 번호에 강함 | 동의어("휴가"↔"연차") 못 찾음 |
| **하이브리드 (EnsembleRetriever)** | 둘의 약점 보완 | 가중치 튜닝 필요 |
| + Reranker (bge-reranker-v2-m3) | 상위 결과 정확도 향상 | 검색이 느려짐 |

**정리:** 하이브리드로 시작 → Phase 3 평가 지표를 보고 Reranker 추가 여부 결정.
BM25 한국어 토큰화는 kiwipiepy 사용 (섹션 4).

## 10. 조합안 비교

| | **A. 전부 로컬** | **B. 혼합** | **C. 전부 외부** |
|---|---|---|---|
| 임베딩 | bge-m3 | bge-m3 | OpenAI |
| LLM | Ollama 로컬 모델 | OpenAI/Claude API | OpenAI API |
| 보안 | ★★★ | ★★ | ★ |
| 답변 품질 | ★★ (모델 의존) | ★★★ | ★★★ |
| 응답 속도 | ★ ~ ★★★ (GPU 의존) | ★★★ | ★★★ |
| 운영 비용 | 무료 (하드웨어 필요) | 사용량만큼 | 사용량만큼 |
| 구축 난이도 | 중 (Ollama 설치·모델 선택) | 하 | 최하 |

공통: PyMuPDFLoader · 정규식 조 단위 분할 · Chroma · 하이브리드 검색 · Gradio

### 추천
1. **코드는 A/B/C 전환이 가능하게** 만든다 (`.env`의 `EMBEDDING_PROVIDER`, `LLM_PROVIDER` 값만 바꾸면 되게).
2. **임베딩은 처음부터 bge-m3로 고정** — 임베딩을 바꾸면 인덱스를 다시 만들어야 하므로, 어느 조합이든 공통으로 쓸 수 있는 것으로.
3. 보안 확인 전까지는 **A(전부 로컬)로 개발**, 승인되면 B로 전환해서 품질 비교.

## 진행 시 데이터 원칙
- 개발·테스트는 **가상의 규정 샘플 PDF**(예: 가상 회사 "복무규정")로 진행한다.
- 실제 사내 규정 원문은 이 대화에 붙여넣지 않고, 완성된 코드를 **본인 PC/검증 환경에서** 실제 파일에 돌린다.
- 스크립트는 작성만 하고, 실행과 최종 검증은 담당자가 한다.
